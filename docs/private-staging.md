# Private phone test preparation

This is a reviewable release template. No deployment, running service, URL, database creation, DNS change or purchase is authorized by this preparation. Production remains blocked until genuine provider credentials and a separate deployment decision exist. Use the dedicated private images and compose file only.

The private build displays **Private test version · synthetic data**. It uses the unchanged beta authentication, secure same-origin cookies, OTP expiry, session binding, account deletion and database persistence. Only `synthetic@example.test` is allowed through its email gate. `NODE_ENV=test` and `EMAIL_TRANSPORT=test` are fixed in this private compose variant; the normal image remains production and existing Resend requirements are unchanged. Never put a real address, route history or personal information into this test database.

## Artifacts and validation (no deployment)

Run `node --test scripts/release/*.test.mjs`, `node scripts/release/private-catalogue.mjs --dry-run` and `node scripts/release/private-import.mjs --dry-run`. These tests use fake libpq executables, in-memory SQL responses and stubbed child processes; they do not contact or create a database. The fixture generator emits two explicitly fictional catalogue records, with no occurrences, results, scores or fabricated analytics. It cannot write to a database. The optional guarded importer described below is prepared but has not run. Empty catalogue and insufficient evidence remain honest states until a separately approved import.

The coordinator can build images after assembling and reviewing the RC. No service launch is implied by a build. Record the RC's full Git SHA, approved base-image digests, build command, resulting image IDs and OCI revision labels. Set `RELEASE_COMMIT` to that SHA on all three builds. Set `VITE_PRIVATE_STAGING=true` on all three for consistent build artifacts. Targets: `private-api`, `private-web`, `migrate`. Use pinned `NODE_IMAGE` and `CADDY_IMAGE` digests at release time; Dockerfile tag defaults are development conveniences and must be resolved/reviewed first. Example build shape, executed only by the coordinator:

```sh
docker build --target private-api --build-arg RELEASE_COMMIT="$REVIEWED_COMMIT" --build-arg VITE_PRIVATE_STAGING=true --build-arg NODE_IMAGE="$NODE_IMAGE" --build-arg CADDY_IMAGE="$CADDY_IMAGE" -t "compass-private-api:$REVIEWED_COMMIT" .
```

Repeat for `private-web` and `migrate`. Use immutable inspected image IDs or registry digests in actual external bindings, never mutable tags. Verify the web artifact includes the banner and each image's `org.opencontainers.image.revision` equals the reviewed SHA. The image review record is external mode-600 JSON with `commit`, `privateBanner: true`, `API_IMAGE`, `WEB_IMAGE`, `MIGRATION_IMAGE`, each exactly matching the inspected result. The record documents the coordinator's inspection; preflight does not contact Docker or attest the record itself.

## External prerequisites and future owner approval

Before any later launch, the owner must approve the isolated staging database, private network interface/firewall and phone CA trust. No existing application/production database may be used. Database credentials must be scoped to a separately supplied `compass_private_synthetic` (or `_suffix`) database at a literal private IPv4 address. No fresh database is created by these scripts. Avoid URL query overrides; only `sslmode` is accepted. Runtime and migration wrappers check the actual database name and reject unknown schemas, non-synthetic users/catalogue provenance, and any historical results/scores. They never reset or delete data. Migrations are still a database write and require the later isolated staging decision.

Copy the three example env templates to an external secure directory, **outside every checkout, build context, static web root, and synced/shared folder**. Use mode 600 for all actual env files and the image record. Do not source these files or run `docker compose config` into logs: rendered configurations can reveal secrets. No secret is committed. Preflight accepts plain unique `KEY=value`, optionally single-quoted values, without interpolation. Generate a fresh auth secret and a bcrypt access hash through an interactive local operator command; never pass a password as a process argument. Basic authentication covers every route, asset, worker, manifest and API request. The outer Authorization header is removed before API forwarding; application cookies remain intact. No HTTP mailbox, inbox static mount or OTP endpoint exists.

Create the external operator directory with mode 700, owned by the image's node UID/GID (1000:1000), and precreate `otp.jsonl` mode 600 with the same ownership. It is mounted only into the API, never web. Operator access requires filesystem privileges on the private host. Keep the inbox out of logs, backups shared with others, screenshots and chat. Restrict retention to this private exercise and securely remove it after shutdown when no longer needed.

Supply `tls.crt` and `tls.key` from an owner-controlled private CA in a separate mode-700 TLS directory, both mode 600. Own the directory and files as the private web runtime UID/GID 1000:1000 (accounting for any host user-namespace mapping). The image removes the base Caddy binary's privileged-bind file capability and runs as UID 1000 on port 8443 with all runtime capabilities dropped. The server certificate must have the selected interface IP as an IP SAN and be currently valid, with a matching private key. Keep the CA root private key elsewhere; only the server certificate/key are mounted. There is no ACME, public HTTP listener or automatic certificate purchase. The owner installs only the public CA root on their own phone and explicitly enables trust, then removes that trust after the exercise.

Default binding is `127.0.0.1:8443`. A phone requires an owner-approved VPN/private interface and routing/firewall restricted to the owner's device. Allowed addresses are loopback, RFC1918 or Tailscale IPv4; public/wildcard addresses fail preflight. For any nonloopback interface, set `STAGE_APPROVED_VPN_IP` equal to `STAGE_BIND_IP` only after the owner approves that interface. That binding is an approval assertion, not VPN discovery. No ports 80/443 or API ports are published. The API's main server binds loopback inside its container; only the synthetic gate is available to the private compose network.

Before setting that assertion or launching anything, the operator must independently verify the IP belongs to the approved VPN interface and the host firewall permits only the owner's VPN device. A private LAN IP alone does not establish the required access boundary. Preflight cannot perform or certify those checks.

Run the read-only preflight before a separately approved launch:

```sh
node scripts/release/private-preflight.mjs --env /secure/compass-private/compose.env --record /secure/compass-private/image-record.json --checkout "$PWD"
```

Preflight checks permissions, interface assertion, immutable image record, exact synthetic database target and external operator/TLS files. It starts nothing, checks no live DB, and does not validate certificate cryptography. The coordinator must separately verify certificate dates/SAN/key match, pinned image provenance, network/firewall isolation, host mounts and all-route basic authentication before owner access. Invoke compose only with `--env-file /secure/compass-private/compose.env -f deploy/compose.private.yml`; never merge the development compose. An explicitly approved migration would use its `operations` profile and guarded `migrate` service. Do not invoke raw Prisma directly against this target.

## Optional two-event catalogue import, only after separate write approval

Preparation does not authorize running this command. After the owner approves the isolated database and the coordinator applies guarded migrations, the optional `catalogue` operations service can add the two exact generated fictional events. Stop the stage API during this operation, use the reviewed migration image from the same RC, and retain the isolated database. No caller-supplied file, URL, name, coordinates, source or identity is accepted. The wrapper validates the exact reviewed fixture, explicit synthetic target and exact database-name confirmation, then runs `checkDatabase()` for read-only actual identity and provenance inspection before creating a private temporary fixture or dispatching the existing `CatalogueImportService` CLI. Temporary JSON has mode 600 and is removed on success or failure. The existing CLI performs schema validation and its transactional source-identity upsert; this command never invokes reset, deletion, user, performance, result or score tooling.

The default and `--dry-run` invocation validate locally and contact no database. An eventual apply command, shown for review only and **not executed during preparation**, is:

All stage database wrappers reject ambient `PG*` environment bindings, including libpq service, connection, credential and search-path overrides. Supply the connection only through the reviewed `DATABASE_URL`; the guard and child importer share that constrained environment. This restriction applies to these private stage wrappers; the separate backup/recovery scripts deliberately use externally reviewed libpq bindings.

```sh
docker compose --env-file /secure/compass-private/compose.env -f deploy/compose.private.yml --profile operations run --rm catalogue --apply --confirm-database compass_private_synthetic
```

Use the exact configured `_suffix` name instead if applicable. Omitting `--apply`, omitting/mismatching confirmation, public/unexpected DB targets, non-fixture rows and an altered fixture all fail closed before dispatch (or remain a local dry run). Repeat apply preserves the two stable external identities and does not duplicate events or touch personal history; it still writes a new audit import run and updates event provenance/import timestamps through the existing importer. Idempotence here means stable catalogue identities/content, not zero repeat writes. Its generated active catalogue does not fabricate historical analytics. Check the CLI summary for two accepted records and zero rejections before restarting the stage API; stop for investigation on failure without reset or cleanup of database rows.

## Phone walkthrough after separate launch approval

1. Connect the owner's phone to the approved VPN/private network. Trust the supplied public CA root. Open `https://<approved-private-IP>:8443` and enter the external access-barrier credentials. Confirm the private test banner. A certificate warning is a stop condition, not an instruction to bypass TLS.
2. Request a code for `synthetic@example.test`. On the private host, the owner retrieves only their synthetic code using `node scripts/release/private-otp.mjs --inbox /secure/compass-private/operator/otp.jsonl --email synthetic@example.test`. Enter it promptly; the normal five-minute expiry remains. The CLI prints one code to the operator terminal only; it does not upload anything or expose a web inbox. It cannot infer expiry from the legacy test transport record: an expired code must be requested again.
3. Check onboarding, country/date filters, event details after the separately approved optional synthetic catalogue import, manual synthetic performances, profile changes, sign-out/sign-in persistence and account deletion. Without that optional import the catalogue remains empty. Missing historical confidence/scores should stay explicit. Use made-up values only.
4. On an approved installed PWA, check the reviewed offline workflow, update/reconnect behavior and sign-out clearing. Basic-auth credentials may need re-entry in standalone mode on some phones; record this as a test finding. Offline previously authorized shell/data can remain locally available according to the PWA's cache policy; the server barrier protects all network requests and does not remotely revoke a device's existing cache.
5. From an unauthenticated client verify `/`, a JS asset, manifest, service worker and `/api/health` all return the access challenge. Verify authenticated TLS works, the certificate matches the IP, no API host port is reachable and no unauthenticated OTP path exists. Do not run these network checks until the owner authorizes runtime.

## Readiness, recovery and rollback

Ready to review means static guard tests pass, full coordinator tests/build pass, RC/image IDs and labels are recorded, genuine production credentials remain absent, and no stage service has been launched. Ready for a later phone exercise additionally requires the isolated supplied DB, guarded migrations, valid trusted private TLS, external secret/mount permissions, owner-approved interface/firewall and successful authenticated/unauthenticated smoke tests. Those remain external prerequisites, not completed facts.

Record the previous paired API/web IDs and schema version before a later change. Roll back only the paired images when the schema is compatible; do not undo migrations or delete volumes/databases. Stop application writes first if compatibility is uncertain. Retain the isolated database for investigation/recovery; never run `down -v`, reset, drop, or destructive seed as rollback. The supplied `backup.sh`/`restore.sh` are preparation only: use external libpq bindings without URL arguments, archive mode 600, and separately reviewed isolated targets. Restore refuses a nonempty target and has no `--clean`/`--create`; no actual restore was run here. A successful archive listing is not a restore rehearsal. A later rehearsal and verification need their own approved isolated recovery database.
