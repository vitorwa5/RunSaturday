# B4.1 — coordinate history operations with authentication

Continues PR #4 from `69d7289106e486fddbbfbc3872fc77333c22d6f9`; implementation `8bb4fdf`. Existing commits, the wider release candidate and other worktrees are preserved. No merge, deployment, production data change or upstream data access is part of this repair.

## H1 cause and correction

The server-side sessionBinding and replay-date correction already exist. The remaining H1 gap was that browser preview, commit and withdrawal did not hold the existing authentication Web Lock. Response cancellation and cross-tab notifications alone cannot serialize an operation with cookie transitions.

`auth/historyOperation.ts` uses the existing `withAuthLock` and exact `5k-compass-auth` key. Each operation captures its originating account ID, mode, sessionBinding and expiry. After acquiring the lock it checks its ticket and reads the authoritative `/api/account/session`, then checks the actual account, binding and expiry again. A stale operation is rejected before any history request is sent. Same-account replacement sessions are rejected too. A missing Web Locks capability fails closed using the existing browser-compatibility safeguard.

The lock encloses request dispatch, response parsing and completion. Once a history request is dispatched, it deliberately does not receive the auth epoch's abort signal: aborting fetch would release the lock while the server might still be processing it. The stale ticket is checked after completion, so a delayed result cannot restore obsolete UI. Authentication transitions queue behind the same lock. Session-rejection notification does not await another lock, and mutation invalidation occurs after the operation leaves the lock; there is no nested acquisition.

Preview calls the helper directly. Commit and withdrawal invoke it inside their mutation function, with both originating identity and dispatch closure captured when the mutation is submitted. An updated React render cannot replace a queued operation's session or binding. Other performance mutation behavior remains unchanged.

No API, data model, scoring or planner code changes. M1 continues to restore a manually edited date on the original CSV record, with destination collisions preserved as conflicts.

## Operational limit

A slow or unresolved in-flight history request holds the authentication lock until it settles, so account transitions can wait. Releasing it early on cancellation would violate H1. Already authorized A writes may finish for A before a queued transition; they cannot be retargeted to B. Server binding/ownership checks remain in place as an independent boundary.
