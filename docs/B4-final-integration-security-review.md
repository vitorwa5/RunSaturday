## Compatibility and privacy boundary

- The session response adds `sessionBinding` beside the existing mode/user/expiry fields. Inspected `AuthProvider.tsx` at both `1fd215c` and `99165a0`: it consumes the JSON object without a strict runtime schema, retaining the existing fields. Old main clients do not send a new mandatory header because B4 introduces none.
- Old B4 history clients omit the new body binding. `history/routes.ts` accepts its omission in the input schema, then authenticates from the cookie and returns beta `409 session_changed` before history reads/writes/deletion. This is intentional fail-closed compatibility: an old import must reload before it can proceed. Existing API tests explicitly exercise missing, stale, cross-account and same-account replacement bindings with store spies and unchanged database rows. A binding never selects an owner.
- Deploy the compatible API before or atomically with the new assets. New H1 web against the old strict history body schema can receive a validation rejection for the added field; reverse-order availability is not established by old-client/new-API compatibility.
- The new client retains H1's immutable originating session and dispatch closure, revalidates under the shared browser auth lock, and retains that lock until the response body completes. The cookie-derived owner and M1 body precondition remain authoritative on the server. Browser lock limitations across crashes/transport failure are unchanged from the H1 review.
- `PrismaDataStore` replans against owner-filtered current rows inside the owner-row-locked mutation, constrains CSV updates/deletes by owner/source, forces CSV/unverified provenance, and invalidates private derived snapshots atomically. B4 does not write public results or scores. Client parsing does not store the original file.
- Independently executed `git diff --quiet` for `apps/web/vite.config.ts` and `apps/web/src/main.tsx` against both base/main: unchanged. Vite PWA remains `autoUpdate`, with shell precaching, `/api/` navigation fallback denial and no configured runtime API caching. API identity middleware sets `Cache-Control: private, no-store`. This is source evidence; cache behavior on an actual production host is a separate deployment check.

## Remaining risk and next workstream

**High, pre-existing on main: general stale-session intention is not enforced on all personal endpoints.** A missed account-transition notification can leave an old A view making a non-B4 private read or prepared action using a replacement B cookie; cookie ownership alone correctly selects B but does not express A's original intention. B4 limits this gap for history operations and does not newly introduce the wider risk. Earlier whole-release rejection in `independent-pr4-pr5-security-review.md` concerns that broader release scope, not a new B4 integration regression.

Highest next workstream: **CENTRAL session-intention enforcement for every personal read/write and cookie transition**. Reuse and reconcile `50c9134` from candidate `eca92e2`; do not blindly merge the older release candidate over the newer H1 implementation. Inventory private derived analytics, profile/settings, performances, favourites, export/deletion and login/logout; require originating binding centrally with narrowly documented health/session-bootstrap/OTP-send exceptions. Preserve signed-out login intention, same-owner replacement rejection, cookie-based ownership and immutable originating transport.

Integration dependency: adapt CENTRAL transport to H1's shared lock, captured session/dispatch, and retained lock through response completion. Require independent QA/security on the resulting exact head, including suppressed-notification A-to-B and same-A replacement for personal reads/writes and queued/dispatched B4 operations. Explicit negatives must send stale/missing bindings directly, rather than allowing a positive-test helper to refresh the intention first. Re-run old-client compatibility: central enforcement changes the API contract beyond this B4 gate.
